# Barua Key Package and Recovery Design

Status: v3 implementation design

This document refines the key-management ideas in `context.md` using the
threat model in `threat-model.md`.

## Design decisions

1. The account password is both the normal login secret and the daily letterbox
   unlock secret. The browser derives a key from it and uses that key to unwrap
   the random vault key; there is no second daily passphrase.
2. New identities use a random vault key wrapped by both the account password
   and the offline recovery phrase. The recovery phrase is for forgotten
   passwords and emergency recovery, not envelope opening.
3. A trusted browser may also receive a non-exportable device key generated by
   the Web Crypto API. That device key protects a local copy of the random
   vault key and makes subsequent operations even more seamless.
4. The server receives public keys and an opaque encrypted key package only.
5. The recovery phrase restores the same stable identity; it does not silently
   create a new identity.
6. Existing v1 packages may still contain a vault-passphrase wrapper. They
   require a one-time migration while the old wrapper is unlocked; this cannot
   be done cryptographically without one of the old unlock secrets.
7. The client uses a well-reviewed cryptographic library. Barua must not
   implement cryptographic primitives itself.
8. Every encrypted package is versioned so the format can evolve safely.

## Implementation choice

Barua will use the official `libsodium.js` browser wrapper, exposed to the
application through a small `baruaCrypto` module. The implementation uses the
`libsodium-wrappers-sumo` build because the selected release's standard build
does not expose the Argon2id password-hashing API required for client-only
vault protection. The larger bundle is an intentional trade for keeping the
complete primitive set in one implementation.

The initial primitive mapping is:

- XChaCha20-Poly1305-IETF for authenticated encryption
- Libsodium public-key encryption for wrapping per-letter content keys
- Ed25519 signatures for sender authenticity
- Argon2id via `crypto_pwhash` for recovery-phrase derivation
- Argon2id via `crypto_pwhash` for account-password derivation
- Libsodium secure random generation for keys, salts, nonces, and IDs
- Web Crypto AES-GCM for the local device-key wrapper

The browser code must access these primitives only through `baruaCrypto`; views
and templates must not call the library directly. The package version and
generated browser bundle will be pinned and tested with known test vectors.

This is a Proton-like one-password experience, but the current Django
authentication flow still receives the password during login. The stored
package and database remain blind to letter contents; an actively malicious
server that changes the login page could still capture a password. Removing
that remaining active-server exposure requires an OPAQUE/PAKE authentication
design and is a separate future security milestone.

## Browser compatibility

The client targets current standards-based desktop and mobile browsers,
including Chrome/Chromium, Edge, Firefox, Safari, and their mobile variants.
It does not identify or special-case a browser by user-agent. Automatic device
unlock requires the standard Web Crypto `SubtleCrypto` API and IndexedDB, which
are available in supported browsers when running in a secure context (HTTPS or
localhost). When those APIs are unavailable, Barua uses an encrypted
 browser-local storage fallback. If all persistent storage is blocked, the
 current login session supplies the account password to the client-side unlock;
 ordinary letter operations still do not request the recovery phrase.

The implementation is present in `frontend/crypto/` and is bundled to
`core/static/core/crypto-bundle.js`. It covers identity creation, recovery,
remembered-device unlocking, letter encryption/decryption, signature
verification, and tamper rejection. Django stores the resulting opaque package
through the authenticated `crypto/identity/` endpoint.

The signup identity-setup flow generates a 24-word English BIP39 recovery phrase
with `@scure/bip39`. The browser normalizes and validates the phrase before
using it as the recovery wrapper secret. The phrase is shown once, must be
manually confirmed, and is paired with an account-password wrapper. It is not
requested during ordinary letter writing.

Contact connections and the encrypted composer are implemented. Connection
codes snapshot both users' key IDs and fingerprints. A new connection is
sendable immediately when those snapshots are current; fingerprints remain an
advanced manual-verification option. A key change blocks sending until the
relationship is re-established.

Recipient reading is now implemented for text letters. The recipient-only
envelope endpoint returns ciphertext plus the sender's public-key record; the
browser checks that the public keys match the recorded fingerprint, unlocks the
recipient identity, verifies the sender signature, checks the authenticated
encryption, and displays the plaintext. The server never performs that
decryption.

## Cryptographic identity

Each user has one active cryptographic identity consisting of:

- An encryption keypair used to protect per-letter keys
- A signing keypair used to prove that a package came from the claimed sender
- A stable key identifier and a human-readable fingerprint

The server stores the public keys, key identifier, fingerprint, and encrypted
private-key package. It never stores either private key in plaintext.

The selected primitives and package mapping are recorded above.

## Key hierarchy

The client generates a random 256-bit vault key, `K_vault`.

The private encryption and signing keys are serialized into a private-key
bundle and encrypted with `K_vault` using authenticated encryption:

```text
private key bundle
        |
        | authenticated encryption with K_vault
        v
encrypted private-key bundle
```

For a new identity, `K_vault` is wrapped by the account password and recovery
phrase:

```text
account password --KDF--> K_account --wraps--> K_vault
recovery phrase  --KDF--> K_recovery  --wraps--> K_vault
```

On a remembered browser, a non-exportable Web Crypto AES-GCM device key wraps a
local copy of `K_vault` in IndexedDB. If that standard facility is unavailable,
Barua uses a randomly generated local device key to encrypt the same local
record in browser storage. Neither form goes to the server. The fallback is
less resistant to someone inspecting the browser profile, so shared computers
should never be remembered.

The private-key bundle should include the key material and format metadata, but
not the user's account password, vault passphrase, or recovery phrase.

## Key package format

The server-facing package should contain fields conceptually equivalent to:

```json
{
  "format_version": 1,
  "key_id": "stable-identity-id",
  "encryption_public_key": "...",
  "signing_public_key": "...",
  "fingerprint": "...",
  "encrypted_private_bundle": {
    "ciphertext": "...",
    "nonce": "...",
    "algorithm": "..."
  },
  "account_wrap": {
    "ciphertext": "...",
    "nonce": "...",
    "purpose": "account",
    "salt": "...",
    "kdf": "argon2id13",
    "kdf_parameters": {}
  },
  "recovery_wrap": {
    "wrapped_vault_key": "...",
    "salt": "...",
    "kdf": "...",
    "kdf_parameters": {}
  }
}
```

The old optional `passphrase_wrap` field remains accepted for v1 compatibility,
but new packages do not include it. Encoded binary values need an explicit
encoding, and the authenticated data must bind the package version, key ID, and
public-key fingerprint to the encrypted bundle.

## Account creation flow

1. The user creates a Django account with an account password.
2. The browser generates the encryption and signing keypairs.
3. The browser generates `K_vault`.
4. The browser creates a high-entropy recovery phrase and displays it once.
5. The user confirms that the recovery phrase has been saved.
6. The browser encrypts the private bundle and creates both the account and
   recovery wrappers.
7. The browser uploads only the public keys and encrypted key package.
8. The browser unlocks the identity locally with the account password and
   creates the remembered-device record.
9. The server marks the cryptographic identity as ready.

The account password is submitted to Django for authentication and is also
processed locally by the browser. The recovery phrase is processed only in the
browser.

Signup must not complete cryptographic setup silently. If key generation or
recovery-phrase confirmation fails, the account should remain clearly marked as
not ready to send or receive encrypted letters.

## Normal unlock flow

1. The user logs into Django normally. The login page carries the password to
   the current tab only long enough for client-side unlock.
2. The browser retrieves the encrypted key package.
3. If a remembered device exists, the browser unwraps `K_vault` locally without
   user input and decrypts the private bundle.
4. If no device exists, the browser uses the account password locally and
   creates a new device record. A normal letter never asks for the recovery
   phrase.
5. Private keys remain in memory only for the active operation where practical.
6. The browser clears unlocked key material after the operation or when the
   page is closed.

The server should never receive an unlock request containing the recovery
phrase.

## Recovery flow

Recovery restores the existing cryptographic identity; it does not generate a
new keypair.

1. The user authenticates the Django account through the normal account flow.
2. The browser downloads the encrypted key package.
3. If the account password has been forgotten, the user enters the recovery
   phrase in a dedicated recovery flow, not in the composer or envelope view.
4. The browser derives `K_recovery`, unwraps `K_vault`, and decrypts the same
   private bundle.
5. The browser creates a new account wrapper and remembered-device record after
   the user chooses a new account password.

The public keys and key ID remain unchanged, so existing letters remain usable.

## Lost-secrets behavior

If the user loses all remembered devices but has the recovery phrase, recovery
is possible.

If the user loses both, the existing private key cannot be recovered. The user
may create a new cryptographic identity, but:

- Existing letters for the old identity remain inaccessible.
- Pending letters addressed to the old identity cannot be decrypted.
- Contacts must be told to use the new public-key fingerprint.
- The old identity should be marked inactive rather than silently replaced.

## Letter encryption package

For each letter, the sender's browser should:

1. Generate a fresh random content-encryption key.
2. Encrypt the canonical letter bytes with authenticated encryption.
3. Wrap the content key to the recipient's verified public encryption key.
4. Optionally wrap a second copy to the sender if sent letters must remain
   locally recoverable before deletion.
5. Sign the package with the sender's private signing key.
6. Upload ciphertext, nonce, wrapped keys, signature, key IDs, and non-secret
   metadata.

The authenticated data should bind the ciphertext to the letter ID, sender
key ID, recipient key ID, format version, and relevant delivery metadata. This
prevents undetected substitution or mixing of package components.

The current browser composer encrypts letter text with this envelope and sends
it as JSON. The server validates only the envelope's version, algorithm, field
shape, size, recipient relationship, and key IDs. It stores the envelope as an
opaque `.barua` file and never receives or transforms the plaintext.

## Contact key verification

Creating a contact does not by itself prove that a public key belongs to the
person the user intended to contact. The contact flow should therefore:

- Record the public-key fingerprint seen when the relationship is created
- Display the fingerprint to both users
- Provide a clear verification state
- Require explicit handling when a key changes

The one-time connection code establishes the relationship in the application.
This is trust-on-first-use: it is convenient for ordinary users, while users
who care about an active server impersonation can compare fingerprints through
another trusted channel before manually verifying the contact.

## Remaining implementation decisions

Before writing production crypto code, decide and record:

- Whether senders receive a wrapped copy of their own letter key
- Key rotation and revocation behavior
- How the browser bundle is built, reviewed, and integrity-protected
- PDF generation and the final letter document format
- Recipient-side PDF decryption and display/download UX

The browser KDF settings also require calibration on representative desktop
and mobile devices before production. They must remain expensive enough to
slow guessing without making normal unlock unusable.

## Device and privacy tradeoff shown to users

Barua should explain the convenience honestly:

> This browser can open your letters automatically after you sign in. Anyone
> who can use this remembered browser profile may be able to do the same. Do
> not remember a shared computer.

The recovery phrase is the high-value backup and should be requested only for
setup, a new browser, or recovery—not during ordinary letter writing.

## Letter retention

The recipient browser acknowledges an open only after successful local
verification and decryption. That acknowledgement starts a short cleanup
grace period; the current implementation uses seven days. The maximum delivery
retention period should also be enforced by the cleanup job.

Deletion reduces operational exposure but does not erase ciphertext already
included in server backups. It complements rather than replaces encryption.
